# 团队代码评审清单 v1.0（review-checklist.md）

> 实验：Lab 7 代码评审实战　|　提交物：`docs/team/review-checklist.md`
> 用途：每位成员评审 PR 时逐项核对，至少留 5 条实质意见。

---

## 一、评审维度与检查项

### 1. 正确性（Correctness）
- [ ] 逻辑是否实现需求，边界情况是否处理（空值、极限值、并发）
- [ ] 状态流转是否正确（如问题/回答/投票状态机）
- [ ] 是否有明显 bug 或死代码

### 2. 可读性（Readability）
- [ ] 命名是否语义化、无歧义
- [ ] 函数/方法是否职责单一、无过长方法
- [ ] 是否有无意义注释或缺失必要注释

### 3. 可测性（Testability）
- [ ] 是否包含对应单元测试，断言是否有效（非"无效断言"）
- [ ] 测试是否覆盖关键业务规则与边界
- [ ] 是否使用适当测试手段（ArgumentCaptor 验证副作用等）

### 4. 安全（Security）
- [ ] 是否硬编码密码/密钥（应走环境变量/Secrets）
- [ ] 是否有注入风险（SQL、XSS）、越权访问
- [ ] 输入是否做校验

### 5. 性能（Performance）
- [ ] 是否无 N+1 查询、无循环内重复 IO
- [ ] 是否合理使用缓存/分页
- [ ] 是否有明显不必要的开销

### 6. 风格与规范（Style & Convention）
- [ ] 是否符合团队规约（提交前缀、命名、DDD 分层）
- [ ] 是否有遗留 TODO / 未清理代码

---

## 二、评审流程约定

1. 每个 PR 至少 1 名非本人成员评审，回复 **LGTM** 后 SM 合并。
2. 评论要**具体、可操作**（给出位置 + 问题 + 建议），避免空泛。
3. 至少 5 条实质意见，可按上述维度逐条给出。

## 三、评审输出模板

```
文件：xxx.java
问题：...
维度：正确性
建议：...
严重度：☐ 阻塞 / ☐ 建议
```
